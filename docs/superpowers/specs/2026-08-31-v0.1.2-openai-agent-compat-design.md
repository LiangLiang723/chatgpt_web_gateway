# V0.1.2 OpenAI-Compatible Agent Compatibility Design

## 1. Goal

V0.1.2 closes interoperability gaps found after V0.1.1 when ChatGPT Web Gateway is used by Cherry Studio and OpenAI-compatible coding agents. The target clients for this maintenance release are Cherry Studio, Pi, OpenClaw, Hermes Agent, and Codex CLI. Claude Code is explicitly out of scope because its native protocol is Anthropic Messages rather than the Gateway's OpenAI-compatible surface.

The release must keep the Gateway's strict public boundary: known compatibility metadata is accepted explicitly at the HTTP adapter and then ignored when it has no executable meaning. Arbitrary unknown request fields remain invalid.

## 2. Root causes

Two independent compatibility failures were observed:

1. Cherry Studio replays Assistant history with `reasoning_content`, while the strict Chat Completions Assistant message schema only allowed `role`, `content`, and `tool_calls`. Ajv therefore rejected an otherwise valid multi-turn request before normalization.
2. Agent clients send provider/runtime metadata such as `store`, `reasoning_effort`, `reasoning`, `parallel_tool_calls`, `service_tier`, cache/session metadata, and richer Responses tool declarations. The previous top-level strict schemas rejected these known fields even when the Gateway could safely consume them as compatibility-only metadata.

V0.1.1 also returned only snake_case model metadata. Cherry Studio's current model representation has camelCase fields such as `inputModalities`, `outputModalities`, `supportsStreaming`, `contextWindow`, `maxInputTokens`, and `maxOutputTokens`, so the Gateway exposes both conventional snake_case hints and those aliases for clients that preserve them. Current Cherry source also shows an important limit: its generic `openAICompatibleFetcher` maps only remote `id/name/owned_by` into `toModel()` and initializes `capabilities=[]`, so the current Cherry client drops these extra `/models` fields before its model editor. V0.1.2 must document that client-side limit instead of claiming the Gateway alone can auto-populate that UI.

## 3. Chat Completions compatibility

The Chat Completions schema remains `additionalProperties: false`, but explicitly accepts the known client fields required by current OpenAI-compatible agents.

Assistant history accepts `reasoning_content`, `reasoning_details`, refusal/annotation/audio metadata, and optional message `name`. These fields do not enter `NormalizedRequest`; authoritative historical Assistant content remains the public `content` text and tool calls.

Top-level compatibility metadata such as `store`, `reasoning_effort`, `reasoning`, `parallel_tool_calls`, `service_tier`, provider options, prompt-cache/session fields, and similar request knobs are accepted and recorded in `diagnostics.ignoredParameters`. They do not alter Browser prompts or fabricate unsupported server behavior. `stream_options` remains strict: only the already-approved `include_usage?: boolean` member is accepted.

Function declarations accept the OpenAI `strict` compatibility flag but continue to normalize only name, description, and parameters into the Gateway's external-function protocol.

## 4. Responses compatibility

Responses accepts current Codex request metadata (`parallel_tool_calls`, `reasoning`, `store`, `include`, prompt-cache fields, `client_metadata`, and related compatibility fields) without leaking them into the Conversation core.

Responses input accepts the richer message/function-call history emitted by current agents, including message IDs/status metadata, namespaced function calls, custom-tool calls, and function/custom-tool outputs.

### 4.1 Namespace bridge

Responses `namespace` declarations are flattened into the existing `NormalizedTool` function representation using an internal `namespace::name` function name. When the Gateway emits a Responses function call, the encoder restores the original `namespace` and `name` fields. The Conversation engine and persistence schema therefore do not need a new tool kind.

### 4.2 Custom/freeform bridge

Responses `custom` tools such as Codex `apply_patch` are adapted to the existing external-function request protocol as a function with one required string property named `input`. Internally the call arguments are JSON `{ "input": "..." }`. Responses encoders restore these calls as `custom_tool_call` items and emit `response.custom_tool_call_input.delta/done` for streaming.

This bridge preserves freeform text but does not claim that ChatGPT Web natively supports OpenAI custom tools.

### 4.3 Server-side tools

Responses declarations such as `web_search` and `tool_search` are accepted only as compatibility metadata and filtered before the Conversation engine. The Gateway does not execute OpenAI-hosted web search or tool-search services and must not expose fake calls for capabilities it cannot perform. Current Codex fields for these declarations are explicitly schema-listed rather than enabling arbitrary request properties.

## 5. Model metadata

`GET /v1/models` continues to expose only `chatgpt-web` and now advertises the implemented chat-model characteristics in both snake_case and Cherry-compatible camelCase forms:

- capabilities: reasoning, image recognition, file input, function calling, structured output;
- input modalities: text and image;
- output modalities: text;
- streaming support;
- context-window, maximum-input-token, and maximum-output-token compatibility hints.

Runtime configuration adds:

- `MODEL_CONTEXT_WINDOW`, default `128000`;
- `MODEL_MAX_INPUT_TOKENS`, defaulting to the configured context window;
- `MODEL_MAX_OUTPUT_TOKENS`, default `32768`.

These are compatibility hints only. They are not claims about an official fixed ChatGPT Web backend limit. They are visible in the raw Gateway response and available to clients that parse them, but current Cherry's generic OpenAI-compatible model fetcher discards them. The chat model still does not advertise `image-generation`; image generation remains a separate endpoint.

## 6. Safety and compatibility boundaries

- Unknown top-level fields and unknown fields inside strict nested objects remain rejected.
- Compatibility-only reasoning metadata is not replayed into the Browser prompt and the Gateway does not fabricate reasoning output.
- Server-side OpenAI tools are filtered instead of executed or impersonated.
- Caller-defined function/custom tools remain external operations: the Gateway requests calls from ChatGPT, but the client performs the actual operation and returns the result.
- No Anthropic Messages endpoint is added; Claude Code remains out of scope.

## 7. Verification

Deterministic coverage must include:

1. Cherry Studio multi-turn Assistant history with `reasoning_content` through real Fastify schema/normalizer routing.
2. Pi/OpenClaw/Hermes-style Chat Completions metadata accepted and dropped at the adapter boundary.
3. The current Codex Responses shape, including function, namespace, custom/freeform, web-search/tool-search declarations and request metadata.
4. Namespace/custom call normalization and Responses non-stream/stream re-encoding.
5. `/v1/models` camelCase + snake_case metadata and configurable token-limit hints.
6. Full `corepack pnpm verify`, repository checks, and `git diff --check` before merge.

Because the implementation does not change Browser selectors, persistence schema, Docker runtime, or ChatGPT Web execution semantics, this maintenance release does not require a new Docker image build or authenticated ChatGPT E2E to validate the adapter-only compatibility changes. Existing real-Web evidence remains the Browser baseline.
