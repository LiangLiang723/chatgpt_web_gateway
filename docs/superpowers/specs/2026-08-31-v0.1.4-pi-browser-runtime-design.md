# V0.1.4 Pi Browser Runtime Compatibility Design

**Status:** implementation and feature-branch verification complete; Git integration/closure pending.

## Problem

V0.1.3 accepts Pi/OpenAI-compatible request shapes, but a real Pi coding-agent request still fails after HTTP/SSE startup with `browser_unavailable` when the request combines a large project system prompt with the normal tool set. The same provider/model succeeds without tools, and small tool requests already pass the existing Phase 7 authenticated E2E.

The current Browser Driver has one size-sensitive boundary that matches that failure pattern: every prompt containing a newline is injected into ChatGPT by dispatching one synthetic `text/plain` clipboard paste event. A large Pi system prompt plus 16 tool definitions substantially enlarges the generated Context Prompt and therefore enlarges that single paste transaction. The public error mapping then collapses any unknown Playwright/Page failure into `browser_unavailable`, so the exact browser-side exception is not present in ordinary Gateway logs.

This maintenance patch must fix the browser transport without silently dropping tools or rewriting the caller's system instructions.

## Browser prompt input

Keep the already-proven input paths for small requests:

- single-line prompt: `keyboard.insertText()`;
- ordinary multiline prompt: one ProseMirror `text/plain` paste transaction.

For large multiline prompts, do **not** dispatch one large clipboard paste. Enter text through bounded keyboard insertions and explicit `Shift+Enter` line breaks so ProseMirror receives ordinary editor input without triggering ChatGPT's large-paste path. Bound each `insertText` operation to a small UTF-8-safe JavaScript string chunk. The switch is based on total UTF-8 prompt bytes, not tool count or client identity.

The Gateway does not truncate tool definitions, cap the number of caller tools below the existing protocol limit, or remove system/developer instructions. That would make coding agents fail semantically even if the browser request appeared successful.

## Failure diagnostics and logging

`asChatGptDriverError()` remains the public stability boundary: clients still receive stable error codes/messages and never receive Playwright internals. For unknown Page/Playwright failures, however, the wrapped `ChatGptDriverError` also carries a bounded local diagnostic snapshot captured at the failure point:

- Driver operation name;
- Page URL;
- Page title when readable;
- `document.readyState` when readable;
- whether the Page is already closed;
- prompt character count / UTF-8 byte count / line count for send failures;
- underlying error name/message/stack through the normal `cause` chain.

No prompt text, tool schema, tool arguments/results, cookies, API key, Profile path, or proxy credentials are recorded.

Both normal HTTP execution failures and SSE failures that occur after HTTP 200 must emit a structured server-side error log containing the stable execution code, safe Driver diagnostics, and underlying error chain. The public OpenAI-compatible response remains unchanged.

## `/v1/diagnostics` active ChatGPT probe

V0.1.3 diagnostics only reports local process/Page counts and `auth_state=not_probed`. V0.1.4 makes an explicit authenticated `GET /v1/diagnostics` request perform one bounded ChatGPT homepage probe when Browser runtime is available:

1. acquire one Page lease from the existing PagePool without evicting or navigating a retained Conversation Page;
2. navigate that leased Page to `https://chatgpt.com/`;
3. run the existing auth probe/Composer detection;
4. report `auth_state=authenticated|auth_required|unknown` plus a bounded probe status and safe page URL/document state;
5. release the Page lease in `finally`.

If Page capacity is exhausted or the probe fails, diagnostics reports the probe failure state instead of disturbing active Conversation affinity. The endpoint may now contact ChatGPT **only because the operator explicitly called diagnostics**. It still does not expose prompt/tool/content data, cookies, API key, Profile path, or proxy credentials.

## Proxy consistency

The formal Compose boundary should allow the same host proxy to be used by Chromium and generic container tooling without `127.0.0.1` accidentally referring to the container itself.

- Keep `CHATGPT_PROXY_SERVER` optional and authoritative for Chromium.
- Pass optional `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, and `NO_PROXY` through Compose.
- Add `host.docker.internal:host-gateway` for Linux Docker Engine deployments.
- Document `http://host.docker.internal:7890` as the container-safe form when the proxy listens on Docker host port 7890.
- Do not commit a mandatory proxy default; deployments that do not need a proxy remain direct.

## Verification

1. Composer-input regression: a large multiline prompt must use segmented keyboard input rather than a single paste transaction, while small multiline and single-line behavior stays unchanged.
2. Driver error regression: unknown Page/Playwright failures retain the underlying cause and safe page/prompt diagnostics without prompt contents.
3. HTTP and SSE logging regressions: mapped execution failures are logged even when SSE has already returned HTTP 200.
4. Diagnostics route/runtime regressions: explicit diagnostics performs the bounded active auth probe, releases its Page, and reports capacity/probe failures without disturbing execution.
5. Compose/config/documentation checks cover host-safe generic proxy passthrough.
6. Focused compatibility tests, then fresh `corepack pnpm verify`.
7. Authenticated real ChatGPT check using `http://192.168.3.83:7890`: fresh diagnostics/inspect plus a Pi-sized system + 16-tool request must complete through the Browser path. Run the real request matrix once after deterministic implementation is complete; do not repeatedly create ChatGPT conversations while debugging.
