# V0.1.3 Client Continuity Compatibility Design

**Status:** complete; implementation, validation, `main` integration, and push closed.

## Problem

Two compatibility regressions remain after V0.1.2:

1. The reported Pi 400 can be reproduced exactly when a user message is serialized as one text content object (`content: {type:"text",text:"..."}`) instead of a string or one-element array. Fastify then emits the same `messages/1` role/content/tool-call union error sequence seen by the client. Pi/OpenAI-compatible histories can also carry Assistant `reasoning`, `reasoning_content`, or `reasoning_text` replay metadata, so the maintenance boundary must accept those known fields without making the message schema open-ended.
2. Cherry Studio sends ordinary OpenAI Chat Completions with full message history but does not expose its internal `topicId` as `X-Conversation-Key`. The Gateway therefore treats every request as anonymous FRESH, creates a new ChatGPT Web Conversation, and replays history into a synthetic prompt instead of continuing the existing Web Conversation.

The second behavior also explains the reported loss of visible Markdown structure in ChatGPT Web history: prior Assistant turns are no longer the original rendered Web turns when every client turn is rebuilt into a new Web Conversation.

## Compatibility boundary

### Pi request/message compatibility

Keep strict message-role validation. Extend `user.content` with one narrow non-standard compatibility shape: a single `{type:"text",text:string}` object. It normalizes to the same single canonical text part as a string or one-element text array; image/file objects are not accepted in singleton form.

Also add only the two Pi/OpenAI-compatible Assistant replay fields that are still missing:

- `reasoning?: string | null`
- `reasoning_text?: string | null`

Together with existing `reasoning_content` and `reasoning_details`, these fields are compatibility metadata and are ignored by normalization; visible Assistant text remains authoritative history.

### Anonymous full-history continuation

`X-Conversation-Key` remains authoritative whenever present. For requests without it, the Conversation Engine may reuse a persisted anonymous Conversation only when all of these are true:

- the request can be canonicalized without unresolved attachments;
- the request is full-history, not incremental-only;
- a persisted anonymous Conversation is clean and has a restorable ChatGPT Conversation URL;
- the existing Context Sync planner classifies the candidate as APPEND or RESTORE, which requires identical instructions, tool fingerprint, and exact stored-history prefix with exactly one pending turn;
- exactly one anonymous candidate satisfies those requirements.

If zero or multiple candidates match, keep existing FRESH behavior. This deliberately prefers a new Web Conversation over silently merging two ambiguous client topics.

The matching logic is protocol-neutral because it works on normalized/canonical requests; Cherry Studio is the motivating client, but other OpenAI-compatible clients that resend complete history benefit without client-specific heuristics.

## Markdown behavior

No DOM-to-Markdown reconstruction is introduced in this maintenance patch. The direct fix for the reported Web-side formatting regression is to stop recreating the Web Conversation on every Cherry turn: APPEND/RESTORE preserves the original ChatGPT Assistant turn and its rendered Markdown in the same Web Conversation.

REBUILD remains an explicit recovery path and may still use canonical text replay; source-Markdown reconstruction is outside this regression fix unless real E2E evidence shows formatting loss after ordinary APPEND/RESTORE.

## Persistence and concurrency

Add a repository/store read constrained by the exact confirmed history length (`synced_message_count`) for clean anonymous Conversations with a persisted ChatGPT URL. Candidate selection is read-only and must not assign a fake public conversation key.

Once a unique anonymous Conversation is selected, serialize that continuation using an internal queue key derived from the persisted Conversation id. After acquiring that queue slot, re-run the same unique-candidate proof before executing: another concurrent anonymous request may have advanced the Conversation between the initial lookup and the queued work. If the expected candidate is no longer the unique APPEND/RESTORE match, fall back to FRESH instead of REBUILDing or overwriting the advanced Conversation. Explicit keyed requests continue to serialize on their public conversation key.

## Verification

2. Schema + HTTP regression for known Assistant `reasoning` and `reasoning_text` replay metadata.
3. Conversation Engine regression proving two unkeyed full-history Cherry-style turns reuse the first ChatGPT Conversation URL and send only the current user text on turn two.
4. Ambiguity regression proving two identical anonymous histories do not get merged.
5. Streaming restart/RESTORE regression proving an anonymous persisted Conversation can be continued after Page affinity is gone.
6. Existing keyed, attachment, tool, streaming, and strict-schema tests remain green.
